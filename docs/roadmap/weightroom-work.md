# WeightRoomGym Work — the arc's schedule

**Started 2026-09-09** (row W0, from the operator interview of the same day). The fifth
application — WeightRoomGym, the host operator's console — in execution order, one row per model
session. Rationale lives in [ADR-0123](../adr/0123-weightroom-is-a-host-operator-tool-above-the-layer-rules.md)
– [ADR-0127](../adr/0127-every-application-publishes-its-settings-schema-and-weightroom-generates-the-form.md)
and [`apps/weightroom/`](../apps/weightroom/spec.md); the plan the rows execute is
[`apps/weightroom/development-plan.md`](../apps/weightroom/development-plan.md); model choice
follows the [model-assignment guide](model-assignment.md) (§3.5: one model per phase, the
stronger; §2.12: overnight rules).

**This is the first arc with a file of its own.** [`outstanding-work.md`](outstanding-work.md)
carried every row from A1 to W0 and had grown to three hundred lines of mixed arcs; from W0 on,
each arc the operator starts gets its own `roadmap/<arc>-work.md` in this shape, `outstanding-work.md`
keeps only its pre-existing rows plus an index of the arc files (its §1.2), and
[`roadmap/README.md`](README.md) lists every work file. Status marks (**done <date>** with the
handoff link in the `#` cell), the `docs/history/handoffs/<ROW>_HANDOFF.md` rule and the kickoff-prompt
convention (`docs/history/prompts/w<N>-….prompt.md`, its **Row:** line naming this file) are identical to
the original's. All paths are relative to `~/ai/suite/WeightRoom/docs/`.

**How to use a row.** Copy the row into a session and hand it its kickoff prompt from
`history/prompts/`; every prompt carries the standing preamble by reference (§2). Rows are listed in
execution order; §3 says which orderings are load-bearing.

## 3. Which orderings are load-bearing

* **W0 before everything** — the ADRs before any code, the standing rule.
* **W1 before W2** — no process control before the login and the audit log exist (security
  before reach).
* **WM before W3** — the shell is built on 0.3's tokens; building it on 0.2.2 and re-skinning is
  the work twice. Soft only if WM slips: W3 may pin MirrorWall as an editable path install with a
  `TODO: re-pin on publish`.
* **WS1–WS4 before W4** — hard: the forms are generated from the documents. The four rows are
  independent of each other and of W1–W3, so they can run in parallel with W1–W3 on Sonnet.
* **W4 before W6 and W7** — the application tokens (W4's tokens pages, W1's wizard) and the
  connection strings (from the schema documents) are what chat and the database viewer read.
* **W7 before W8** — delete-with-cleanup and restore are curated operations over the guard's
  machinery.
* **WA1 before W8** (operator, 2026-09-10) — soft on the code, hard by decision: the
  `adapters_registered` gap is closed while FreeWeight's schema is not yet under W8's catalog, and
  W8 then starts from FreeWeight's new revision in `known_revisions`.
* **WI1 before W10** (operator, 2026-09-10) — W10's verification exercises the console's Settings
  page against all four applications, and IdeaPress's half of it only works once WI1 lands.
* **W1–W10 strictly in order otherwise**; W5 (docs) is the one flexible row — any time after W3.
* **WM2 after W10** — adoption targets a released MirrorWall 0.3 and a released WeightRoomGym.
* **The WP arc: W10 → WP1 → WP2 → WPC1 → (WP3 ∥ WP5) → WP4 → WP6** (operator, 2026-09-10; WP3 and WP5 in parallel amended the same day, replacing WP3 → WP4 → WP5) — WP1's page kit and API client come first; WPC1 follows WP2 so it builds on the kit WP2 has corrected, and precedes WP3–WP6 so the verification sees PromptCadence's pages on its API; WP3 before WP4, a hard dependency: WP4's calibration run reuses WP3's run-event proxy. WP5 is independent of WP3 and WP4 in substance. It shares only `rendering.py` (`_APP_PAGES`, `_PAGE_HREF`, `_PAGE_PHASE`), the §14 audit registry, the OpenAPI snapshot, `api.md`, `CHANGELOG.md` and this file. So WP3 and WP5 run at the same time, under these rules:
  * **Branches.** Each row has its own branch and worktree, created from `main`: `row/wp3-freeweight-pages` at `~/ai/worktrees/weightroom-wp3`, and `row/wp5-ideapress-pages` at `~/ai/worktrees/weightroom-wp5` (`git worktree add -b <branch> <path> main`). Neither row commits on `main` in `~/ai/suite/WeightRoom`. A worktree has no virtualenv: run the gate with `~/ai/suite/WeightRoom/.venv` and `PYTHONPATH=$PWD/src` (`history/handoffs/W4_HANDOFF.md` §2.2). Component work stays in the row's own component, on that repository's `main` as usual: FreeWeight for WP3, IdeaPress for WP5. A changed `api.md` is edited on the row's branch first and then mirrored.
  * **Throwaway consoles.** WP3 uses `127.0.0.1:8779` and WP5 uses `127.0.0.1:8789`, each with its own XDG tree. Neither row restarts `weightroom.service` (the operator's console on 8769) before its merge.
  * **One live model load at a time.** A FreeWeight suite run and an IdeaPress stage run never run on the reference machine together (memory safety, ADR-0119). The operator attends both rows and says which demonstration goes first. Gates and tests against fixtures run in parallel freely.
  * **Merge.** The operator merges the row that finishes first into `main`. The second row then merges `main` into its branch. It resolves `rendering.py` and the §14 registry by keeping both rows' entries. It regenerates the OpenAPI snapshot and `api.md` in a scratch XDG tree, and never hand-merges them. It keeps both rows' `CHANGELOG.md` entries and both rows' marks in this file. It runs the full gate again before its own merge, and its handoff records the merge.
  * **WP4** starts from `main` once WP3 is merged. If WP5 is still open, WP4 takes WP3's place under these rules, with its own branch and worktree, and port 8779 once WP3's console is stopped.
  * **WP6** starts once WP4 and WP5 are both merged.
* **The WPF rows, from WP6's findings (2026-09-11):** **WPF1 before WPF2**, because WPF2's
  demonstration saves FreeWeight's settings through the form WPF1 fixes. WPF3 (PromptCadence), WPF4
  (LoadCoach and the console's unit verbs) and WPF7 (IdeaPress) are independent of the others in
  substance.
  WPF1, WPF4, WPF5 and WPF6 all edit WeightRoomGym, and WPF5 edits `rendering.py`. Run those one at
  a time, or on branches under the parallel-row rules above.
